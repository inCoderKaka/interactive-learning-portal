## 1. What local-server is (context)

A small Go app on a **host machine** that sits in front of a local model runtime, the **engine** (Ollama). It gives **consumers** and **client apps** authenticated, metered access to the host's models.
- The **host** issues access keys and sets each consumer's **grant**: allowed models, quotas, context and output limits, concurrency, expiry and allowed request properties. The host also decides **resource requests**.
- Consumers reach the host over **Tailscale**, on the host's tailnet. An opt-in public mode through Tailscale Funnel is planned for phase 2.
- Every metered answer carries a host-signed **usage receipt**.
- The host stores **no prompts or responses** by default.

personal-assistant is the other client app, and it moves to the same contract in the same release (local-server req_002 D-18).

**What the portal may run on a host (req_002 D-16):**
- any **text task** the learner points at `local`;
- **`vision.describe`**, which sends an image (§3, R-12).

Realtime voice (`interviewer.realtime`) stays on cloud providers. local-server keeps a seam for a future audio API, not designed yet.

## 2. What the portal must fix and do now, against the API as built

**R-1 Call the host from a server route, never from the browser (req_001 D-148, D-163; req_002 D-02).** The consumer API answers no CORS headers and accepts only access keys, never cookies. The portal's `local` provider today calls `<localUrl>/v1/chat/completions` and `/v1/models` from the browser (`lib/interview/providers/llm.ts` is `"use client"`; also `lib/ai.ts`), so it cannot work against a real host.

What the portal must do:
- Move every `local` call behind a **server-side route of the portal**, for example a Next.js route handler.
- Keep the access key on the server: an environment secret on Vercel, or a server-side setting when the portal is run locally.
- Never send the key to the browser.

**R-2 Address and key.**
- **Base URL:** the host's tailnet name, `https://<host-machine>.<tailnet>.ts.net:8484/v1`. 8484 is the default; the host may change it with `serve.tailnet_consumer_port`. On the host machine itself it is `http://127.0.0.1:8484/v1`.
- **Default to fix:** the portal's default `localUrl` is `http://localhost:8080` (`lib/store.ts`), which is wrong for local-server. Use 8484.
- **Access key:** `ls_<prefix>_<secret>`, sent as `Authorization: Bearer ls_<prefix>_<secret>` on every `/v1` call.
- **Device binding:** a host can tie a key to one tailnet device. A tied key used from another device answers `invalid_api_key`, so the key must be issued for the device or node that makes the calls (R-3).

**R-3 Reaching the host from the Vercel deployment (req_002 D-10, D-22). Risk: unproven.**
- **The plan:** the portal's Vercel function joins the host's tailnet **from inside the function**. It uses the userspace-networking pattern Tailscale documents for AWS Lambda: `tailscaled --tun=userspace-networking` with a local SOCKS5 or HTTP proxy that the function's `fetch` goes through.
- **Credentials:** it joins with a **tagged, ephemeral auth key** held as a Vercel secret. The tag's grant (Tailscale ACL) reaches only the host's consumer API port.
- **Unproven:** that `tailscaled` runs inside a Vercel function at all, its cold-start cost, and whether userspace mode resolves MagicDNS names. Tailscale's serverless page does not list Vercel.
- **Limits to plan around:**
  - Vercel functions run at most 300 s on the Hobby plan, streaming included;
  - an instance is paused after its requests;
  - `/tmp` is writable;
  - Vercel daemons are beta and take no traffic;
  - Tailscale's Personal plan includes 1,000 ephemeral-node minutes a month (not enforced).
- **No fallback relay:** there is no relay and no spike-then-fallback. If the pattern does not work on Vercel, the hosted portal has **no `local` provider** until local-server's public mode (phase 2), and the learner's tasks fall back to their cloud providers.
- **Running the portal locally:** a machine already on the host's tailnet needs none of this. The server route calls the tailnet name directly.

**R-4 Build the capability table from the host, not a constant (req_002 F-03, D-13).** The portal's capability table marks `top_k` and the presence and frequency penalties as supported for `local`. A host as built refuses them with `400` `unsupported_parameter`. The rules:
- **Today**, a `local` call may send only:
  - `model`, `messages` (text; roles `system`, `user`, `assistant`);
  - `max_tokens` or `max_completion_tokens` (not both), `temperature`, `top_p`, `seed` and `stop`;
  - `stream` and `stream_options.include_usage` (needs `stream: true`).
- **Refused today:**
  - any other field, for example `top_k`, `frequency_penalty`, `presence_penalty`, `response_format` other than `text`, `tools`, or `reasoning_effort`;
  - image parts.

  The answer is `400` `unsupported_parameter`, with `param` naming the field. It is never silently ignored, which matches the portal's own rule that unsupported settings are shown, not dropped.
- **Show the gaps:** the portal's settings panel shows those as unsupported for `local`, and `vision.describe` on `local` is unavailable until §3.
- **Limits:** read them from `GET /v1/capabilities`: per-model `context_limit` and `max_output_tokens` (null means the host default applies), `on_context_overflow`, `allowed_request_properties`, quotas, the rate limit and `expires_at`.
- **Models:** `GET /v1/models` lists only the models the grant allows.
- **After §3:** the whole table comes from discovery (R-8).

**R-5 Fallback and errors.** The portal's task profiles already carry a fallback. Errors are the OpenAI envelope `{"error": {"message", "type", "param", "code"}}` with a typed `code`; honour `Retry-After`. Fall back when:
- the connection fails or times out;
- `GET /v1/health` shows `sharing_state` other than `sharing` or `engine_state` `unavailable`;
- the call answers one of:
  - `host_paused` (503) or `engine_unavailable` (503);
  - `queue_full` (429) or `quota_exceeded` (429), or `outside_time_window` (429);
  - `model_not_granted` (403) or `policy_denied` (403);
  - `over_budget` (422) or `rate_limit_exceeded` (429);
  - `invalid_api_key` (401), which is also a configuration problem to show the learner.

`context_too_long`, `unsupported_parameter` and `invalid_request_properties` (400) are request-shape errors. Fix the request instead of retrying it.

**Budget for the rate limit:** every `/v1` call spends the key's rate allowance (60 requests a minute by default), `/v1/health`, `/v1/models` and `/v1/capabilities` included. So cache status and discovery on the server, briefly.

**R-6 Streaming and receipts.**
- **Streaming:** `stream: true` gives server-sent events ending in `data: [DONE]`. An error after the stream started arrives as a `data:` line holding the error envelope.
- **Receipts:** every metered answer carries a signed usage receipt:
  - in `LS-Receipt` on a non-streamed call;
  - in an SSE comment line `: ls-receipt <JWS>` before `data: [DONE]` on a streamed call. Standard SDKs skip comment lines, so the server route reads the raw stream.
- **What to keep:** the receipt's `usage_id`, with the call record (R-14).

**R-7 Usage and asking for more.**
- **Usage:** `GET /v1/usage` (`granularity` `minute` | `hour` | `day`, with `from` and `to`) gives the key owner's usage.
- **Asking for more:** `POST /v1/resource-requests` asks the host for more (a model, context, quota or access), with comments. The host can also use local-server's consumer web page for both, so the portal need not build them.

## 3. The planned client contract (local-server phase 2, req_002) — DESIGNED, not built

Every new field is **optional**: a call that sends none of it works as in §2 (req_002 D-12). Until this ships, nothing below exists on a host.

**R-8 Capability discovery (req_002 D-13, D-23).**
- **`GET /v1/capabilities`** gains, per model and for the calling key:
  - the standard fields and engine options the model supports, with their ranges;
  - the grant's **defaults** (a client value replaces them, within the caps);
  - **forced values** (they replace the client's value);
  - **resource caps** (`context_size`, the output length, `keep_alive`, thinking allowed or not).
- **`GET /v1/models`** gains an OpenRouter-style `supported_parameters` name list per model.
- **What the portal must do:** build its `local` capability table and settings panel from that answer, and send nothing discovery does not list.
- **Not exact for one call:** discovery shows grant-level values and does not apply the host's policy rules. For a single call, the effective-options header (R-11) is the truth.

**R-9 New standard fields (req_002 D-12, D-24, D-27, D-38).** These map from the portal's `GenParams`:
- **`frequency_penalty`** and **`presence_penalty`**: from `frequencyPenalty` and `presencePenalty`.
- **`response_format`** (`text`, `json_object`, `json_schema`): from `responseFormat`. It uses the engine's constrained decoding. The host does not validate or repair JSON (D-35), so the portal keeps validating its schema and owns retries and fallback, as its task profiles already do.
- **`reasoning_effort`** (`none`, `low`, `medium`, `high`): from `reasoning.effort`. `reasoning.budgetTokens` has no equivalent; a numeric thinking budget is only noted as a future option.

Thinking, when on:
- **Output:** its text comes back in a **`reasoning`** field on the message and on stream deltas.
- **Counting:** thinking tokens count as output, against `max_tokens` (the host adds **no headroom**), the quotas and the receipt.
- **Thinking exhausted:** an empty answer with `finish_reason: length` and non-empty `reasoning`. The TypeScript library raises it as a typed signal. The portal shows it as such and offers a higher cap, lower effort, or the fallback.

**R-10 Engine options object (req_002 D-02, D-03, D-09, D-11).** One namespaced object *(name in spec)* in the chat body carries the options the OpenAI API lacks, under engine-neutral names:

| Option | Maps from the portal's settings | Notes |
|---|---|---|
| `top_k` | `topK` | |
| `min_p` | — | new to the portal |
| `repeat_penalty` | — | new to the portal |
| `context_size` | — | the engine's context window; a resource option with a grant cap |
| `keep_alive` | `promptCaching` (the local stand-in) | how long the model stays loaded after the call, within the host's cap (`scheduler.keep_alive_max`, 1 hour proposed); a model the host pins stays loaded regardless |

An unknown key in the object is `unsupported_parameter`. A value over a resource cap is clamped and reported, never refused (R-11).

**R-11 Effective-options header (req_002 D-06, D-27, D-36).** Every answer, streamed or not, carries a response header *(name in spec)*.
- **Format:** an RFC 9651 dictionary.
- **Content:** each option and sampling value that actually ran. Where it differs from the request, the header gives what was sent (`was`) and why it changed (`by`: `cap`, `forced` or `not_applied`).
- **Overflow policy:** the header also states the policy in force, `refuse` or `truncate`. Under `truncate` the engine may have dropped old messages, so the portal **marks such a call** in its trace as "prompt may have been cut".
- **What the portal must do:**
  - record the header with every call (R-14);
  - show it in developer mode, so a learner sees, for example, `max_tokens` cut from 2500 to 1024 instead of a silent clamp.

**R-12 Image input for `vision.describe` (req_002 D-16, D-28).**
- **Format:** a user message part `{"type": "image_url", "image_url": {"url": "data:image/<type>;base64,<…>"}}`, which is what the portal already sends.
- **Supported models only:** it is accepted only for a model whose capabilities list `vision`; any other model answers `400` `unsupported_parameter` on `messages`.
- **Size:** the whole body is bounded by `limits.max_body_bytes` (8 MiB by default), so scale large drawings down before sending.
- **Storage:** images are never stored or logged by the host.

**R-13 Task tag (req_002 D-15, D-21, D-28).** Name the task behind every call with one key in `LS-Request-Properties`: `task="<task id>"`, using the portal's own task ids (`interviewer.turn`, `summarise`, `extract`, `vision.describe`, `scorecard`, `code.review`, …).
- **Allowed characters:** lowercase letters, digits, `.`, `_` and `-`, at most `policy.task.max_length` characters (64 proposed). A bad value is refused as an invalid header.
- **Grant permission:** the grant must allow the `task` property. Discovery lists the allowed properties; send `task` only when it is allowed.
- **On the host:** usage is broken down by task. `GET /v1/usage` gains a `task` filter and field. Past `usage.task.max_per_window` (50 proposed) distinct tasks per consumer per day, further tasks are recorded as `other`, so keep task ids stable and few.
- **Prompt version:** it stays the portal's own field and is **not** sent to the host (D-36).

**R-14 What the portal must keep for every AI call (req_002 D-33, D-34).** The host stores nothing, so the portal **persists every AI request and response, not sampled**, together with:
- the learner's feedback or comment on it;
- the effective options as echoed (R-11), the overflow policy and the prompt version;
- the model and its fingerprint (R-15), the task (R-13) and the usage id or receipt (R-6);
- latency, finish reason, token counts (reasoning tokens when the engine gives them), a link to the run a regeneration replaced, and any error.

Retention, access and deletion of that store are the portal's to decide. The learner's opt-in for replay recordings (`docs/design/mock-interviewer/01-product-spec.md`, about line 79) **must not** cover the AI call text; that is a separate store with its own rules.

**Tunable steps and side-by-side comparison (D-33):**
- **Tunable:** each AI step (task) has its own parameters and prompt version, which a developer can change and re-run.
- **Comparison:** runs can be compared side by side in the portal's own UI, for example its developer mode and evaluation runner (`04-ai-configuration.md` §6), built from the fields above. The host builds no compare or replay tool.
- **Trace names:** for what the portal records, use the **OpenTelemetry GenAI** attribute names: request and response model, request parameters, finish reasons, token usage.

**R-15 Model fingerprint (req_002 D-32).** The answer's `system_fingerprint`, in the non-streamed body and in every stream chunk, names the exact weights that served the call (built from the engine name and the model digest).
- **Why record it:** a tag such as `llama3.2:3b` can move when the host pulls a new version; the fingerprint cannot. Record it with each run, so a "why did quality change" question can be answered.
- **Lag:** it can lag a pull by up to `gateway.model_info_ttl` (5 minutes proposed).

**R-16 TypeScript client library (req_002 D-13, D-25, D-38).**
- **What it is:** a small library, generated from `api/openapi.yaml` in the local-server repo.
- **Where it comes from:** published to **npm** with trusted publishing and provenance, versioned with semver against the API. The package name and scope are not set up yet.
- **What it wraps:** discovery, the options object, the task tag, the effective-options header and the thinking-exhausted signal, so no `@ts-expect-error` is needed for the extra body object.
- **Where the portal uses it:** in its server route.

**R-17 Pass-through, no surprises (req_002 D-35).** The host serves exactly the model and options the request names, or returns a typed error:
- an unknown model is `model_not_found`;
- an option the model cannot carry is `unsupported_parameter`.

It substitutes no model and falls back to none, so the portal's task profiles keep owning fallback.

## 4. Compatibility standards

- **The surface:** OpenAI-compatible, implemented as published. local-server's additions are separate additive contracts: `LS-*` headers, an SSE comment line, and (planned) one namespaced body object and discovery fields.
- **Versioning:** the major version is in the URL, and changes within a major are additive only, so ignore response fields you do not know. `Deprecation` and `Sunset` headers come before any removal.
- **Conventions:** RFC 9651 dictionaries for `LS-Request-Properties` (and, planned, the effective-options header). IDs are UUIDv7 and times RFC 3339 UTC. Lists use cursor paging.

## 5. Out of scope here

- Any change to local-server (its repo owns that).
- Realtime voice and speech on a host: the audio API is not designed (req_002 D-16).
- Model classes on the host (`fast`, `mid`, `strong`) so presets resolve without model names: scoped for the future (req_002 D-08).
- Host-side storage of AI calls on the client's explicit consent: accepted in principle, off by default, and its mechanism is deferred (req_002 Q-25).
- Tool calling, embeddings `dimensions`, and a numeric thinking budget.

## 6. Open for the portal's own design

- The shape of the server route (one generic proxy route, or one per task), and how it streams to the browser.
- How the Vercel tailnet join is built and tested (R-3), and what the hosted portal shows when it does not work.
- Where the access key and the Tailscale auth key live per environment, and whether one host key serves every learner or each learner brings their own host key (the portal's BYOK rule, ADR 0004).
- Where the AI-call store (R-14) lives (Supabase is the natural place), its retention and deletion, and how developer mode compares runs.
- Which portal tasks default to `local` when a host is configured, and each one's fallback.
